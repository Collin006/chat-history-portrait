# Production workflow

Use this document after `prepare_chat_history.py` succeeds. It defines the filesystem contract and staged analysis protocol.

## Workspace layout

```text
OUTPUT/
├── manifest.json
├── private/
│   ├── corpus.jsonl
│   ├── analysis/
│   │   ├── session-memories.jsonl
│   │   ├── theme-time-map.json
│   │   └── insights.jsonl
│   ├── batches/
│   │   ├── batch-0001.jsonl
│   │   └── ...
│   ├── checkpoints/
│   │   ├── batch-0001.analysis.json
│   │   └── ...
│   ├── evidence-ledger.jsonl
│   ├── profile.json
│   ├── portrait.md
│   └── calibration.json
└── public/
    ├── profile.json
    ├── share-cards.md
    ├── story-angles.md
    ├── site-package.json
    └── privacy-scan.json
```

The preparation script creates `manifest.json`, `private/corpus.jsonl`, `private/batches/`, and empty checkpoint/public directories. Later artifacts are generated by the analysis workflow. `private/analysis/` is created when the first analysis runs. Never put a raw excerpt or source title under `public/`.

## Stage 1: corpus audit

Read `manifest.json` and report:

- active conversation count, user and assistant turn counts, date coverage, and undated fraction
- branch messages excluded from the active transcript
- empty or unsupported messages
- batch count and oversized records
- likely coverage biases, such as a narrow date range or task-heavy usage

Stop if the corpus is empty or the manifest schema is unsupported. Do not claim representativeness merely because the corpus is large.

## Stage 2: batch map

Process every `private/batches/batch-*.jsonl` exactly once unless a valid checkpoint already exists. A checkpoint uses this shape:

```json
{
  "schema_version": "portrait-checkpoint/1.0",
  "batch_id": "batch-0001",
  "claims": [],
  "experiences": [],
  "themes": [],
  "tensions": [],
  "content_seeds": [],
  "contamination_warnings": [],
  "processed_source_refs": [],
  "completed_at": "2026-01-01T00:00:00Z"
}
```

Keep claims atomic. Store a short excerpt only in the private checkpoint and only when necessary to verify meaning. Do not lift assistant assertions into claims. Record possible role-play, third-party, translation, pasted-content, and hypothetical contamination.

After writing a checkpoint, verify that `batch_id` matches the filename and `processed_source_refs` are present in that batch. A later run may resume from valid checkpoints.

### Session-memory pass

After a batch is checkpointed, write concise records to `private/analysis/session-memories.jsonl` for each conversation or coherent conversation segment. A session memory is a retrieval aid, not a profile conclusion: it contains opaque conversation/source references, date range, neutral summary, candidate themes, stated decisions/events, contamination warnings, and an `incomplete_context` flag. Do not assign personality labels here.

## Stage 3: cross-batch reduction

Read all checkpoints. Merge semantically equivalent claims while retaining every distinct supporting and contradicting source reference. A high message count inside one conversation is one context, not repeated evidence.

Create `private/evidence-ledger.jsonl`, one object per claim:

```json
{
  "claim_id": "clm_001",
  "claim_type": "observed_pattern",
  "text": "Draft claim",
  "confidence": 0.74,
  "support": [{"source_ref": "c000123:u0004", "reason": "..."}],
  "counterevidence": [],
  "sensitivity": "medium",
  "status": "pending_user_review"
}
```

Also build `private/analysis/theme-time-map.json`: a map from normalized themes to session-memory references and observed date periods. Absence in a period is not evidence of disappearance.

For every recipe dimension, use the evidence-engine protocol in `insight-system.md`: retrieve support, deliberately seek counterevidence, calculate context and time coverage, and write atomic records to `private/analysis/insights.jsonl`. An insight may be `insufficient_evidence`; that is a valid result. Profile claims and rendered content must be derived from these insights, not generated independently.

Use recurrence across different contexts, longitudinal stability or change, explicit self-description, concrete behavior, and counterevidence to calibrate confidence. Do not use pseudo-precision: scores help rank claims, not prove psychology.

## Stage 4: private synthesis

Write `private/profile.json` according to `private-profile.schema.json`, then a readable `private/portrait.md`. Include:

- scope and limitations
- a concise “portrait in progress”
- specific patterns with counter-patterns
- explicitly stated experiences and transitions
- themes and changes over time
- productive contradictions and unresolved questions
- story-worthy material ranked by resonance and privacy risk

Validate the structured profile before presenting it. If the schema validator reports an error, repair the data rather than omitting the field silently.

## Stage 5: calibration

Ask the user to review the private portrait. Record decisions in `private/calibration.json`:

```json
{
  "schema_version": "portrait-calibration/1.0",
  "reviewed_at": null,
  "decisions": [
    {"claim_id": "clm_001", "decision": "accept", "replacement": null, "note": null}
  ],
  "global_notes": [],
  "public_consent": false,
  "audience": null,
  "identity_mode": null,
  "off_limits": []
}
```

Allowed decisions are `accept`, `edit`, `reject`, and `keep_private`. Rejected claims remain recorded so they cannot reappear during rework. Public generation requires `public_consent: true` plus audience and identity choices.

## Stage 6: public synthesis

Generate only from accepted or edited claims not marked `keep_private`. Follow `public-profile.schema.json` and the editorial framework. Public files use generalized wording and contain no evidence pointers, excerpts, conversation titles, raw timestamps, or third-party identifiers.

Run the package validator and privacy scanner. Review every finding with the user. The final handoff is a local package; uploading it is a separate, explicit action.
